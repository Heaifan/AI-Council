# Communication Protocol v0.1

> 状态：Phase 0 制度冻结版  
> 目标：规定 Agent、主席、秘书、Human Arbiter 之间“如何交换可审计信息”，不提前锁死 Schema 字段名。

## 1. 基本原则

会议通信必须是**结构化、可追溯、可验证、可重放**的。

任何一次模型输出进入正式 Meeting State 之前，都必须被识别为一个明确的会议事件，而不是仅作为 UI 中的一段聊天文本存在。

## 2. 通信参与者

正式参与者类型包括：

- Human Arbiter；
- Chair；
- Secretary；
- Agent；
- Runtime/System。

一个模型实例可以承担一个或多个逻辑角色，但日志与消息记录必须保存其**逻辑身份**，不能因为底层模型相同而合并职责。

## 3. 消息语义合同

每条正式消息至少需要表达以下语义：

- 属于哪一场会议；
- 由谁产生；
- 产生于哪个阶段；
- 面向谁；
- 当前可见性范围；
- 消息正文或结构化输出；
- 与哪些先前事件/Artifact/证据有关；
- 验证状态；
- 是否已被 Runtime 接受。

具体 JSON 字段名在 `message.schema.json` 阶段冻结。

## 4. Agent 输出合同

Agent 不应以完全自由文本作为唯一正式输出形式。

活动 Protocol 应定义当前阶段的输出模板；Agent 根据模板填写，秘书再按结构提取与汇总。

允许底层传输仍使用自然语言，但进入正式会议记录时必须映射到协议要求的结构。

## 5. 可见性

Communication 层必须服从会议 Visibility Mode，不得自行泄露底层模型身份。

### 公开模式

阵营、角色、底层模型均可见。

### 半匿名模式

阵营、角色可见，底层模型隐藏。

### 完全匿名模式

其他参会者仅看到 A1/A2/A3、B1/B2/B3 等代号；真实角色和模型隐藏。

Agent 自身仍能获得完成职责所必需的角色卡和阵营任务。

## 6. 主席/秘书处理边界

秘书可以：

- 提取结构；
- 聚合同类观点；
- 建立观点与来源之间的引用关系；
- 标记冲突、缺失与无法验证的信息；
- 生成中立汇总。

秘书不得：

- 删除对某一方不利但有效的论点；
- 把自己的补充推理写成委员原始结论；
- 以“摘要”为理由改变原观点立场；
- 替 Human Arbiter 做最终决定。

## 7. 编译后的指令可见

Instruction Compiler 为每个 Agent 生成的实际 `InstructionPacket` / Prompt 必须能够在调试或审计界面查看。

显示内容至少应能区分：

```text
系统级约束
Protocol 当前阶段约束
Role Card
Visibility
会议上下文
当前任务
输出合同
```

具体显示 UI 在后续模块设计中确定。

## 8. 校验失败

若模型输出不符合当前 Protocol 的结构要求：

1. 不得静默写入为“有效结果”；
2. Validator 必须给出可定位错误；
3. Runtime 决定是否允许重试、人工修正或进入异常状态；
4. 重试次数属于模块级参数，后续冻结。

## 9. 非目标

本文件不冻结：

- 通用评分字段；
- 所有 Protocol 共用的固定回答章节；
- 具体 Markdown/JSON/XML 视觉格式；
- 自动重试次数；
- Token 预算算法。
